**Decisions I made:**
- **`0009` supersedes `0005` §4, and it is the thing most likely to be
  re-litigated.** Writing `tc_006` surfaced that `human_task_outcomes` has the
  *same* element-id problem `0005` §3 fixed for `TaskStub` — its keys are
  documented as element ids and P2 cannot know an element id. So instead of
  `Assertion.path_match`, `0009` proposes one field, `TestCase.target_match:
  exact | semantic`, governing `must_traverse`, `must_not_traverse` **and**
  `human_task_outcomes` keys. One field, whole case, because a case is emitted
  by one generator with one convention. The failure mode it prevents is nastier
  than §4's: an unresolvable human-task key doesn't fail loudly, it hangs the
  instance and reports `error`, which reads on a corpus run as "the generated
  workflow hangs" — a plausible-looking, completely wrong result.
- **`tc_006` deliberately has no `path` assertions.** With no match marker in
  the frozen type today, a semantic `must_traverse` in the golden example would
  be compared literally against element ids and produce exactly the false
  failure `0009` exists to prevent. Its assertions are `output`/`invariant`/
  `budget`, which need no artifact vocabulary. Add a semantic path assertion and
  a description-keyed `human_task_outcomes` entry the moment `0009` is accepted.
- **Did not add `target_match` to `contracts/intent.openapi.yaml`.** The OpenAPI
  describes what the frozen types *are*; encoding an unaccepted proposal is how
  the two drift. (My D1 handoff said the OpenAPI "encodes §3 and §4" — §3 yes,
  in the `TaskStub` schema; §4 was only ever prose at line 123. Same reasoning.)
- **Manifest `patterns` are derived from the emitted artifact, not hand-tagged**,
  and `--check` asserts declared ⊆ derived. Hand tags rot: the first run of that
  check caught 10 cases declaring patterns their artifact didn't have, and the
  by-pattern coverage table had `message_start: 1` when 6 artifacts had one.
- **Under-specified references are marked `reference_is_ground_truth: false`.**
  An ambiguous prompt has several defensible expansions; scoring alignment
  strictly against one reading punishes a generator for choosing differently.
  What those 10 measure is whether `/v1/spec` raises the right `SPEC-*` code
  instead of inventing the missing detail.
- **`c01` is the negative control** — trigger, threshold, failure path and budget
  all stated, so `expected_diagnostics` is empty. A sufficiency checker is only
  worth having if it stays quiet on a prompt that leaves nothing out.
- **INT severity tops out at `warning` by construction.** `diagnostics.py`
  defines `error` as "blocks a gate", and `IntentReport` has no `gates` field, so
  no `INT-*` code can block anything. I had `INT-CONDITION-NOT-EXPRESSED` as
  `error` and downgraded it. Worth revisiting with P1 at D6 — it means a finding
  as serious as "the user's stated threshold isn't implemented anywhere" cannot
  be escalated above warning.
