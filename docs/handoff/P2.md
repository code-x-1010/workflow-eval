**Decisions I made:**
- **`0009` supersedes `0005` §4, and it is the thing most likely to be
  re-litigated.** Writing `tc_006` surfaced that `human_task_outcomes` has the
  *same* element-id problem `0005` §3 fixed for `TaskStub` — its keys are
  documented as element ids and P2 cannot know an element id. So instead of
  `Assertion.path_match`, `0009` proposes one field, `TestCase.target_match:
  exact | semantic`, governing `must_traverse`, `must_not_traverse` **and**

  by one generator with one convention. The failure mode it prevents is nastier
  than §4's: an unresolvable human-task key doesn't fail loudly, it hangs the
  instance and reports `error`, which reads on a corpus run as "the generated
  workflow hangs" — a plausible-looking, completely wrong result.
- **`tc_006` deliberately has no `path` assertions.** With no match marker in
  the frozen type today, a semantic `must_traverse` in the golden example would
  be compared literally against element ids and produce exactly the false
  failure `0009` exists to prevent. Its assertions are `output`/`invariant`/
  `budget`, which need no artifact vocabulary. Add a semantic path assertion and
  a description-keyed `human_task_outcomes` entry the moment `0009` is accepted.
- **Did not add `target_match` to `contracts/intent.openapi.yaml`.** The OpenAPI
  describes what the frozen types *are*; encoding an unaccepted proposal is how
  the two drift. (My D1 handoff said the OpenAPI "encodes §3 and §4" — §3 yes,
  in the `TaskStub` schema; §4 was only ever prose at line 123. Same reasoning.)

  check caught 10 cases declaring patterns their artifact didn't have, and the

- **Under-specified references are marked `reference_is_ground_truth: false`.**
  An ambiguous prompt has several defensible expansions; scoring alignment

**Decisions I made:**
- **The extractor leaves fields EMPTY rather than guessing them.** `outputs`,
  real step dependencies (prose order only), and which steps sit inside which
  branch are all residue for D4's refiner. Over the 40-case corpus this yields
  115 steps, 17 triggers and **6 branch conditions — all 6 correct**. Six out of
  a corpus with far more numeric conditions in it is low recall, and that is the
  trade: an invented variable name is confident, plausible, and wrong all the
  way through to D8's boundary cases and P4's cost model, whereas an absent one
  is visible at D5 as a sufficiency gap. Half of `tests/unit/intent/test_extract.py`
  is rules *declining*, and every one of those cases is a false positive this
  extractor really produced against `datasets/corpus/` before I tightened it:
  "keep it under 50 cents per invoice" read as a branch on a variable called
  `it`; c05's mid-process join ("When all three are done…") read as the process
  trigger; "anything scoring above 0.8" read as a variable called `anything`.
  Do not raise recall by loosening these without adding the corresponding
  decline test.
- **`/v1/spec` stays stubbed by default.** Real output is much thinner than
  `spec.response.json`, and three agents are wired against that example. The
  stub/real split matches `make dev` / `make dev-real`, which is the repo's own
  answer to this. The contract test drives all 40 corpus prompts through the
  *real* path too — one prompt validating proves nothing about the other 39.
- **Domain nouns that are also verbs** (score, order, claim, credit) nearly cost
  me the condition rule twice. A determiner or a plural marks the noun reading
  ("the score is at least 60", "orders above 500"); without either, a lexicon
  verb before a number is an imperative ("route over 500 to approval"), not a
  condition. Same trap in reverse for steps: a word after a preposition is an
  object, so "10% of invoices need approval" is not an "invoice" step.
